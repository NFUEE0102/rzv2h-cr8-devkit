# 11 — Running the CM33

The CM33 is the third core, driven by standard Linux remoteproc. With the two
R8 cores it completes the three-core setup — verify everything at once with
`sudo python3 ~/r8web/bb.py --all`.

## Start

```sh
sudo ~/devkit/tools/start-cm33.sh cm33_demo.elf
```

The script clears the CM33's MHU doorbell and virtio status bytes, then
starts `remoteproc0`. `cm33_demo.elf` is the stock Renesas rpmsg demo plus
the CM33 black box (see below).

## Rules

1. **Kernel requirement: a 6.10-based kernel** (this image ships one).
   Do not start the CM33 from a 6.18/rz-cmn-3.3-based kernel — its CM33
   remoteproc path hard-freezes the whole machine.
2. **Start the CM33 last, and avoid stopping it.** On stop, the kernel zeroes
   the CM33's registered carveouts; with this image's three-window DT split
   that only touches CM33-owned memory, but the CM33's own resource table and
   black box are wiped — read any post-mortem state *before* stopping.
   `start-cm33.sh` refuses to stop a running CM33 for you.
3. **To swap CM33 firmware**, use the scripted sequence:

```sh
sudo ~/devkit/tools/redeploy-cm33.sh <new.elf>
```

   It stops, installs, restarts, then verifies the R8 cores are intact
   (and rebuilds them only if the board carries an older, unsplit DTB).

## Talking to it

This kernel intentionally has no `virtio_rpmsg_bus`; the userspace OpenAMP
client takes the host role, exactly as with the R8 cores:

- Client: `examples/linux-client` built with `MBX_ID = UIO_RECEIVER1` and the
  CM33 column of docs/09 (prebuilt on the image as `~/r8_bench_cm33`).
- **The CM33 demo carries a single vdev (service 0).** Use the client's
  single-channel form: `platform_init(0, 0, ...)` binding `rpmsg-service-0`.
  The two-channel flow used for the R8 cores waits forever here.

```sh
cd ~/r8_bench_cm33
sudo R8_BENCH_NOTS=1 ./r8_bench_cm33 500     # echo test
```

## CM33 black box

Same idea as the R8 black box, at **phys `0x431F0000`** (CM33 view
`0x831F0000`). Key offsets match the R8 layout (`+0x40` stage, `+0x44`
fault); the magic differs (`BB33`) so tools can tell the core type. On a
HardFault it captures CFSR/HFSR/BFAR/MMFAR plus the stacked PC/LR. Read it
with `bb.py --all` or `bb.py --addr 0x431F0000`. Sources:
`blackbox/cm33_blackbox.{c,h}` — hook `cm33_bb_init()` into
`R_BSP_WarmStart(POST_C)` and pump from any periodic task.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| whole machine freezes on `echo start` | 6.18-based kernel | use this image's kernel; power-cycle to recover |
| `state=running` but client times out on NS bind | client used the two-channel flow | single-channel form (above) |
| R8 cores dead after a CM33 stop | board carries a pre-split DTB (one 63 MB CM33 window) | apply `tools/percore-board.sh` (adds the three-window split), then `restart-r8-pair.sh` |
| `bb.py` shows the CM33 uninitialized right after a stop/start cycle | its black box lives inside the wiped carveout | expected — it re-initializes on the next start; post-mortem reads must happen before stopping |
